# 工作流与提示词

METR 对资深开源开发者的随机对照实验显示，在熟悉的代码仓库里使用 AI 反而平均多花了 19% 的时间。拖慢交付的往往不是模型吐代码慢，而是跳过查现状、定契约和测试约束，直接丢一句话让它开工。代码很快生成出来，开发者的时间全耗在读懂偏离架构的改动、返工和修补边界缺陷上。

想让 AI 在老仓库里少返工，通常得把活拆开：先让它翻一遍现有代码对齐方案，拿测试把预期行为定住，再分批往里写实现。

## 先读后写，拆成两轮

<InkFigure src="/img/four-phases.svg" alt="四步走：探索、计划、执行、验证" />

改一行文案或修个一眼看出的拼写错，直接让 AI 改完跑测试就行，不用走整套流程。但只要涉及新功能或者跨文件改动，第一条消息先别急着让它动代码。它不清楚仓库里早写了多少公共工具和隐性规矩，一上来就改，很容易重复造轮子，甚至顺手把原来的分层搅乱。

第一轮只让它做只读检索，先交一份定位说明和修改清单：

```text
先别改代码，帮我在 src/ 下搜一下现有的同类模块、公共工具和路由是怎么挂的。
把能直接复用的函数或基类（带上路径和名字）、打算新增或修改的文件清单，还有可能跟现有表结构、接口契约冲突的地方列出来，我看完再动手。
```

多花这几十秒，能把「用回旧库」「漏改总路由表」「重写一遍校验函数」这些坑挡在动笔之前。

## 测试先行与最小复现

只对着几句口头需求写代码，模型很容易把模糊的地方顺手猜掉。让它对着已经跑失败的断言或复现脚本去改，目标就清楚多了。平时开发最常用的有两种开头：

### 新功能：先把失败的测试跑出来

```text
按下面这几个入参、返回结构和异常场景，先在测试目录把单元测试补齐，跑一遍确认它们是失败的。
测试覆盖我确认过之前先别写业务代码；后面动手实现时也只改业务代码直到测试全绿，别把已有断言改松或者删掉。
```

### 修缺陷：先拿最小复现说话

贴出报错堆栈、请求入参和触发条件，先让 AI 证明它确实复现到了同一个错：

```text
报错堆栈和触发条件放下面了。先照着写一个最小复现测试或独立脚本跑一遍，确认跑出了一模一样的报错，再把原因和打算改哪几处列给我。
别直接跳过复现去猜着改，也别用空的 try/catch 把异常吞掉。
```

## 局部重构与改动边界

让 AI 顺手重构一段旧代码时，最头疼的是它改着改着就开始「主动优化」。重命名十几个调用点、顺手升个依赖，或者把全文件格式全洗一遍，最后评审人根本看不出真正改了哪。改局部逻辑时，把边界顺嘴说死就行：

```text
只重构 src/services/billing.ts 里的 calculateFee 函数内部，把嵌套拆平就行。
函数签名、返回结构和抛出的异常类型保持不变，别的文件、依赖版本和全局格式都别碰。改完顺手跑一下 npm test -- billing.test.ts，把完整输出贴给我。
```

遇到跨表、跨端的大需求，拆成**数据契约与表结构 → 核心逻辑与单测 → 接口路由与前端联调**三轮推进更稳妥，每过一轮跑通测试、提交一次，再往后接。

## 清会话与子代理隔离

AI 连续改了两轮以上还没修好同一个问题，当前对话里往往已经堆了一堆失效的补丁和互相打架的假设，再往下追问只会越改越乱。这时候停下来，把已经跑通的测试、确认过的接口、剩下的报错和相关文件路径整理成一页[交接单](/templates/handoff)，直接开个新会话接着干。

做跨目录代码调研、文档与实现核对，或者改完后自查时，把只读检索丢给独立的子代理去跑，免得几十个探测文件的全文把主会话的上下文挤满。

## 练习

1. 挑手头一个待开发的新接口或模块，严格按「只读探查列清单 → 确认后先写失败测试 → 写实现跑绿」走一遍完整对话，对比以前直接写完的返工次数。
2. 选一个历史复杂函数，用上面的局部重构提示词约束 AI 只动单文件且跑通原有单测，检查 `git diff` 是否零越界改动。
3. 下次遇到线上或本地缺陷时，强制 AI 先写出能稳定复现错误的最小脚本并贴出失败输出，再允许它动业务代码。

- [METR：AI 对资深开发者效率的影响](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)：英文，重点看实验结论与原因分析。理解为什么盲目让 AI 介入熟悉代码仓反而会拉长交付总耗时。
- [Claude Code 最佳实践](https://code.claude.com/docs/zh-CN/best-practices)：读先探索再规划编码以及验证工作相关小节，中文。这两节拆解了只读检索、测试驱动与子代理隔离的具体做法。
- [Harness engineering for coding agent users](https://martinfowler.com/articles/harness-engineering.html)：读「Feedforward and Feedback」一节，英文。讲清约束文档（前馈）与自动化测试（反馈）如何共同卡住 AI 代码质量。
