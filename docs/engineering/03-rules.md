# 仓库与技能

第二章聊过把个人常用要求写进全局指令，把办公流程打包成技能。可真到了多人共用的代码仓库里，光靠每个开发自己电脑里的提示词根本管不住项目。

团队新同事或跨组支援的研发接手一个老仓库时，常反复问「测试跑哪条命令」「错误码注册在哪」「哪些目录是代码生成器产出的」。想让每个人以及各人手里的 AI 严格按同一套工程约定产出代码，靠群消息提醒无效，必须把约束直接提交进仓库版本库。

## 根目录 AGENTS.md

<InkFigure src="/img/context-layers.svg" alt="一次请求里有什么：系统提示、全局指令、项目指令、技能、对话历史与本次消息" />

现在主流编程智能体（Agent）和 Harness 每次打开仓库，都会优先载入根目录的 `AGENTS.md`（部分工具兼容读取 `CLAUDE.md`）。

写仓库 `AGENTS.md` 最忌讳把项目背景、架构演化史和二十条风格细则全塞进去。指令一长，真正要命的命令和边界反而被淹没。筛查原则就一条：**删掉这句，AI 会不会因此改错代码或越线，不会就删**。通常写清下面这几项，控制在一两屏以内就够了：

1. **分支与开工约定**：拉最新用什么命令，开发分支叫什么，严禁直接推送哪几条分支。
2. **常用精确命令**：安装依赖、本地启动、运行测试、格式或类型检查的完整命令，一个字母别错。
3. **目录结构与禁改区**：只写不明显的地方，比如接口定义在哪个目录、哪几个目录是脚本自动生成的严禁手工编辑。
4. **复用与依赖底线**：动手写新组件前先搜仓库里有没有现成的，新增第三方依赖前必须先问人确认。
5. **必须先报方案、等确认才能干的操作**：比如改数据库表结构、删除或覆盖已有大文件、执行 `git push` 或对测试和生产环境做写操作。
6. **默认验收方式**：改接口要跑哪条测试贴输出，改页面要启动服务开哪几个路由看一眼。

想直接套现成骨架，去拿模板页里的 [代码仓库 AGENTS.md 模板](/templates/agents-md) 改吧改吧就能提交进项目根目录。

## 共享的项目技能

有了管底线的 `AGENTS.md`，开发团队手里还可以多备一层顺手的家伙：**跟着代码一起存进 Git 仓库里的项目技能（Skills）**。

很多开发平时写代码，每次建新模块、加接口、发版前自查，都得自己重敲一大段话，新人接手写出来的结构跟老同事完全两样。把这些带固定步骤和仓库规矩的高频动作打包放进仓库技能目录（例如 `.agents/skills/` 或团队工具约定的位置），全组人拉下代码就能直接调用，做出来的目录和代码风格就能对齐。

代码仓库里最值得先收进项目技能的，通常是这几类活：

- **模块与接口脚手架**：规定新建一个业务模块要建哪几个文件、路由和参数校验怎么写、错误码统一挂在哪里、对应的单元测试长什么样。
- **合并请求交前自审**：按照你们项目特有的规矩，发 MR 前自动检查一遍有没有漏改配置、有没有绕开权限校验、有没有动到不该动的共享表。
- **常见排错与环境检查**：把查日志、查队列、核对缓存或数据库状态的固定只读排查顺序打包好，值班或接手模块时直接调用，避免每次满群问老开发。

搭建项目技能同样不用自己硬背格式。挑出仓库里写得最干净、最符合你们规范的一两个现有模块做样板，连同上面几条注意事项一起交给内置 `skill-creator`，让它顺着样板拆出一套技能提交到仓库里就行。

## 滚动维护规矩

别想着找个周末闭门憋一份五千字完美规范。第一版仓库 `AGENTS.md` 从空文件起步，先写**怎么跑起来、怎么跑测试、哪几件事不能碰**，写几行就够推上去用了。后面顺手按这几条滚动维护就行：

- **同一句话给 AI 交代到第二次**，直接补进 `AGENTS.md`。
- **AI 犯了一个原本能避开的错**（比如用了团队早已淘汰的请求库），复盘时立刻提炼成一句「必须用 X、不用 Y」写进去。
- **厚重的架构文档和接口详情不往里塞**，在 `AGENTS.md` 里只留一句「接口约定见 `docs/api-guide.md`」，让 AI 需要时再去按需翻读。
- **每个月清理一次过时条目**，两条规矩冲突了当场合并，早已重构删掉的目录从文档里清出去。

## 练习

1. 打开你目前负责（或常逛）的一个代码仓库，检查根目录有没有 `AGENTS.md`。如果没有，从 [代码仓库模板](/templates/agents-md) 拷出最核心的「启动命令、测试命令、禁改区、先确认再做的事」先立出第一版（不超过 30 行）。
2. 找一个你组里写得最标准的现有模块或常用检查流程，用 `skill-creator` 打包成第一份放进仓库共享的项目技能，并开个干净会话实测跑一遍。
3. 查一遍手头已有的项目说明文档，把超过五十字的背景科普删掉，只留下「不写 AI 就会犯错」的硬命令与边界。

- [Claude Code 最佳实践](https://code.claude.com/docs/zh-CN/best-practices)：读「保持 CLAUDE.md 简短」「将规则限定到代码库的某一部分」「将团队流程放进 skill」三节，中文。把仓库说明做薄、把大流程拆进按需技能的做法全在这三节里。
- [Anthropic 各团队怎样使用 Claude Code](https://claude.com/blog/how-anthropic-teams-use-claude-code)：读「Product Engineering」和「Security Engineering」两节，英文。看一线研发团队怎么把仓库规矩、交叉评审和自动化检查配在一起用。
