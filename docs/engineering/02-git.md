# Git 与分支

AI 改代码的速度远高于手写，一旦多任务共用工作区或跳过分支保护直接推送，串改文件、冲掉未提交改动和误触发流水线的速度也同样成倍放大。

在团队仓库里和 AI 配合，用 Git 守住三件事就够了：各自工作区互不干扰、每次提交能单独撤回、靠保护分支和评审把门看住。

## 保护分支与环境

团队工程仓库通常会设三条长期保护分支，不允许任何人或智能体（Agent）直接推送提交，所有改动一律从临时特性分支经过合并请求（MR 或 PR）合入。

| 保护分支 | 作用 | 对应环境 |
|---|---|---|
| `master` 或 `main` | 已经正式发布的稳定代码，版本号打在这里 | 生产 |
| `release` | 发版前的集中验收（部分仓库另设 `uat`） | 预发布与验收 |
| `dev` | 日常集成，做完且审过的功能合到这里 | 开发与测试 |

不同仓库的主干命名可能略有差别，哪几条受保护、新分支该从哪条拉出来，进仓库前先看根目录的 `AGENTS.md`，别凭猜测直接拉。

<GitFlowDemo />

临时分支用完、合进长期分支之后就顺手删掉，免得几个月后仓库里挂着几十条没人认得出的死分支：

| 临时分支类型 | 从哪拉 | 合到哪 | 常见命名例子 |
|---|---|---|---|
| 功能开发 | `dev` | `dev` | `feat/feedback-list-filter` |
| 缺陷修复 | `dev` | `dev` | `fix/pay-callback-idempotency` |
| 线上紧急修复 | `master` | `master` 和 `dev` | `hotfix/login-redirect` |
| 文档与杂项 | `dev` | `dev` | `docs/onboarding`、`chore/upgrade-deps` |

## 日常流程与 worktree 并行

进团队仓库干活，顺着下面这个节奏走最不容易撞车：

1. **开工先拉最新**。跑一遍 `git pull --ff-only` 把最新代码拉下来（有子仓也一起同步）。拿着几天前的旧代码让 AI 改，改完一合并满屏都是冲突，得出的结论也跟着跑偏。
2. **拉一条新的特性分支**。例如 `git switch -c feat/简短描述 origin/dev`，把改动关进自己的实验桌。
3. **小步提交并写清原因**。每次提交只做一件能独立说清楚的事，按约定式提交写消息，格式是 `类型(范围): 做了什么`，正文补上为什么要这样改。光写「修改 bug」「更新代码」，过两周连自己都看不懂。
4. **推送并开合并请求**。写清背景、改动、验证和上线注意点，模板见 [合并请求描述](/templates/mr)。
5. **评审合并后删分支**。合并完顺手清掉本地和远端临时分支。

这里顺便提一个开发特别实用的进阶技巧。同时要做两件事的时候（比如一边在开发新功能，一边突然要修个紧急缺陷），**千万别在同一个文件夹里用 AI 来回切换分支**。直接用 `git worktree` 再挂出第二个独立目录：

```bash
git worktree add ../myrepo-fix-pay -b fix/pay-callback origin/dev
```

一个分支占一个干净目录，每个目录单独开一个 AI 会话，两边各改各的互不污染，改完合并后把工作树目录和分支一起删掉就行。

顺手备一张约定式提交的类型表，让 AI 帮写提交信息时直接照这个口径来：

| 类型 | 用于什么改动 | 语义化版本号影响 |
|---|---|---|
| `feat` | 新增功能 | 升次版本（例如 `1.2.0`） |
| `fix` | 修复缺陷 | 升修订号（例如 `1.2.1`） |
| `docs` | 只改文档 | 不影响功能代码 |
| `refactor` | 不改变外部行为的代码重构 | 视需要整理 |
| `test` / `chore` / `ci` | 补测试、调整构建依赖、改流水线配置 | 不直接改变业务逻辑 |

```text
fix(login): 会话过期后跳转地址丢失

会话过期的重定向把原始地址拼在登录页后面，参数被二次编码。
改为在登录前保存原始地址，登录成功后从会话里取回。
```

## 只读查历史与操作红线

要批量清理攒下来的废弃分支，别图省事一句话放权让它直接删，删掉的往往就是同事还没合入的活。稳妥的做法是拆开走：**先只读调查拿清单 → 你逐仓写明保留规则 → 人过一遍将删名单 → 最后再执行删除**。

平时让 AI 操作 Git，这几条底线提前写进会话或项目指令里，能挡住大多数意外：

| 红线 | 为什么要拦住 |
|---|---|
| 权限判断只读不探测 | 查保护分支设置就能知道能不能推，试着往保护分支推一次就会直接触发流水线 |
| 不强制推送、不重置历史、不擅自删分支 | 强制推送和 `reset --hard` 会直接抹掉别人或你之前未推送的提交 |
| 绝不直接向 `master`、`release`、`dev` 写入 | 哪怕当时仓库忘了开保护，改动也必须走分支和合并请求 |
| 提交和推送前必须先给人确认 | 推上远端往往会触发自动构建甚至环境部署，没有撤回键 |
| 提交前看一遍 `git status` 和 `git diff --staged` | 把不小心写进代码里的密钥、本地配置、临时打印文件全拦在提交前 |

有一次，为了验证某个账号能不能往 `uat` 和 `release` 分支推代码，AI 直接往业务仓库的 `uat` 和 `release` 上各推了一个探测文件，紧接着又提了一次撤回。偏偏那两个分支当时没开保护，推送直接成功，把两条流水线全触发跑了起来。真要测权限或写入效果，去自己建的一次性空仓库里试，别拿团队业务仓试手。

## 常见冲突与卡点

| 常见卡点 | 对应做法 |
|---|---|
| 自己的分支落后 `dev` 很多 | 先 `git fetch` 拉取远端最新记录，再把 `origin/dev` 合并或变基进来，解完冲突再推送 |
| 拉代码或合并时出现代码冲突 | 让 AI 把 `<<<<` 到 `>>>>` 两边分别改了什么解释清楚，你拍板留哪边，别让它自己瞎删 |
| 不小心把账号密钥提交进了本地仓库 | 还没推送就立刻撤回或重写本地提交；**一旦已经推送到远端，第一时间去平台作废轮换新密钥**，再找仓库管理员清理历史 |
| 进新仓不知道该从哪条分支拉 | 先看根目录 `AGENTS.md`，没有就问仓库负责人，别靠猜 |

## 练习

1. 如果你平时很少敲 Git 命令，先花二十分钟通关 [Learn Git Branching](https://learngitbranching.js.org/?locale=zh_CN) 的「基础篇」前四关，眼见为实理解什么是提交和分支。
2. 打开你手头正在用的一个仓库（或者自己的小工具目录），用上面的只读提示词让 AI 梳理一遍当前所有分支，看看哪些早该删了。
3. 下次同时要做两个独立改动时，试一次用 `git worktree` 开第二个工作目录并单开一个 AI 会话，体验两头互不干扰的感觉。

## 延伸阅读

- [Learn Git Branching](https://learngitbranching.js.org/?locale=zh_CN)：推荐玩「基础篇」和「远程」，交互式图形化沙盒，把分支拉出、提交、合并的动画走一遍，比死背命令直观十倍。
- [Pro Git 中文版](https://git-scm.com/book/zh/v2)：读第 3 章「Git 分支」的「分支简介」「分支开发工作流」「变基」三节。看完就明白分支其实只是指向某次提交的小指针，心里就不怵了。
- [Gitflow 原文](https://nvie.com/posts/a-successful-git-branching-model/)：看「The main branches」「Supporting branches」和文首 2020 年加的「Note of reflection」。补记说得很清楚，持续交付的轻量 Web 应用不必硬套复杂分支，按团队实际节奏裁剪就行。
